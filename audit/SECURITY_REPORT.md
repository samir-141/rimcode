# Seguridad de RimCode

La revisión cubre la landing, proyectos, legales, consentimientos y las APIs de contacto, chat principal, chat compatible y voz. Los archivos JSON forman el catálogo institucional. El repositorio no contiene autenticación de visitantes, panel administrativo, gestión de roles ni un servicio privado de datos que exponga recursos por identificador.

| Control | Implementación y evidencia |
| --- | --- |
| Entrada y solicitudes desde otros orígenes | Las APIs POST requieren un objeto JSON, comparan `Origin` cuando está presente y rechazan el contexto de navegador de otros orígenes. Se limita la lectura real a 8 KiB aproximados para chat (8192 bytes), 14 000 bytes para voz y 36 000 para contacto. Las APIs públicas admiten clientes HTTP sin cookies ni cabeceras de navegador. |
| XSS y marcos | React representa texto de chat y formularios como texto. El correo HTML escapa los campos y JSON-LD escapa `<`. Los enlaces de proyectos y redes requieren HTTPS. Las demos se sirven en iframes aislados con una lista de orígenes y un enlace directo. |
| Encabezados | CSP en producción, `nosniff`, `X-Frame-Options: DENY`, política de Referer y de permisos, sin `X-Powered-By`. HSTS se activa si la URL pública está configurada con HTTPS. |
| CSP y prerenderizado | Rive se habilita con la opción WASM y sus orígenes solo cuando se configura. Analytics requiere configuración y consentimiento. Las páginas estáticas de Next usan scripts de hidratación en línea, por lo que la política conserva `unsafe-inline` en scripts y estilos. Este control restringe orígenes, objetos, marcos y destinos de formularios. Migrar a nonces requeriría revisar el prerenderizado. |
| Contacto | Validación compartida, honeypot, errores acotados y una clave de idempotencia con hash de campos normalizados y UUID de envío. El proceso agrupa solicitudes simultáneas y recientes. Resend puede deduplicar con su propia clave. El webhook debe respetar la clave para tener la misma garantía entre instancias. |
| IA y datos | El clasificador elige un ID permitido. La API vuelve a resolverlo contra la FAQ y descarta el texto libre del proveedor. Se omiten coincidencias de correo y teléfono. La aplicación no persiste historiales ni registra mensajes, cuerpos de proveedor o credenciales. |
| Voz | Firma HMAC de texto, caducidad y ámbito del visitante, verificada antes de consumir cuota. Upstream fijo y autenticado, sin redirecciones. Los resultados de la API no son cacheables por el navegador o CDN. La caché interna se limita a respuestas públicas y está versionada. |
| Abuso | Los nombres de encabezados de IP confiables se configuran en el servidor. Sin un proxy confiable se emplea un cupo común. Redis REST admite un contador atómico compartido y el servicio falla de forma cerrada cuando Redis está configurado y no responde. La alternativa en memoria es por proceso. |
| Consentimiento | Cookie de preferencias con `SameSite=Lax` y `Secure` en HTTPS. El modal usa el diálogo nativo. GA queda condicionado al consentimiento y se desactiva de forma explícita al revocarlo. El micrófono requiere una acción en el chat. |
| Dependencias | El aviso moderado inicial de `minimatch` estaba en la cadena de ESLint. Se fijó `11.0.1` para esa dependencia transitiva y se comprobó compatibilidad. |

Criterios aplicados a la revisión local. [Prevención de CSRF de OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Request_Forgery_Prevention_Cheat_Sheet.html), [encabezados HTTP de OWASP](https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html) y [prevención de XSS de OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html).

Se inspeccionaron 19 fragmentos JavaScript públicos y se compararon los valores de servidor disponibles sin imprimirlos. Se verificaron dos valores de la configuración local con cero coincidencias. El ensayo de contacto usó datos sintéticos. Las cinco URL de demostración activas respondieron HTTP 200 a una comprobación HEAD y se cargaron en iframes aislados desde las fichas locales en Chrome.

El entorno final de alojamiento deberá verificar que el proxy sobrescriba el encabezado de IP seleccionado y que el origen de Next y el servicio de voz queden protegidos por la red. Faltan una comprobación con Redis real y una propiedad de Analytics real, y la verificación de entrega de correo con Resend. La prueba de contacto usa un receptor HTTP local. [API REST de Upstash](https://upstash.com/docs/redis/features/restapi), [idempotencia de Resend](https://resend.com/blog/engineering-idempotency-keys), [desactivación de Analytics](https://developers.google.com/tag-platform/security/guides/privacy).
